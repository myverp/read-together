# Процес розробки

## 1. Межі задачі

Перед нетривіальною реалізацією коротко визначай очікувану поведінку, обсяг змін і критерії готовності. Переглянь ROADMAP.md, стан Git і відповідну реалізацію. Виконуй найменший завершений крок; не додавай незапитані фічі, рефакторинг чи абстракції. Зберігай сторонні зміни та матеріали. Уточнюй тільки питання, які справді блокують роботу.

## 2. Робоча гілка та релізи

- `main` містить тільки перевірений код готових релізів і є production-гілкою Vercel.
- `develop` — основна робоча гілка для накопичення та спільної перевірки змін.
- Для окремих нетривіальних задач використовуй короткоживучі гілки `codex/<назва-задачі>` від актуальної `develop`; завершені перевірені зміни повертай у `develop` через PR.
- Не реалізовуй звичайні задачі безпосередньо в `main`. Не перенось незавершену роботу між гілками без доручення; за потреби використовуй окремий worktree.
- Регулярно коміть і пуш робочі зміни; push у робочу гілку не є дозволом на production-реліз. Інші гілки Vercel використовують preview.
- Перенесення `develop` → `main`, production-міграції та production deployment виконуй лише за явним дорученням користувача. Це доручення може бути дане заздалегідь; не перепитуй повторно.
- Merge у `main` запускає production deployment через Git-інтеграцію Vercel, тому сам merge також потребує дозволу на реліз. Не обходь це обмеження ручним deployment або promotion preview.
- Планові фічі можна випускати групами. Критичні виправлення можуть мати окремий невеликий реліз. Якщо `develop` містить ще не готові до релізу зміни, узгодь обсяг критичного релізу; не випускай їх разом автоматично.
- Процес залишається простим: без повного GitFlow і постійних release-гілок.

## 3. Коміти та PR

Роби невеликі логічні коміти протягом роботи, після відповідної перевірки. Не накопичуй усі зміни до кінця великого етапу. Додавай у staging тільки файли поточної задачі; не включай секрети, тимчасові файли або сторонні матеріали.

Використовуй PR як місце перегляду змін і результатів CI, а не як формальність. Для робочих PR цільова гілка — `develop`; для релізних — `main`. Описуй проблему, результат і перевірки. Перед merge перевір diff і успішне завершення CI для актуальної версії PR.

`main` захищена вимогою PR та успішних GitHub Actions `checks` і `integration`, з актуальною базовою гілкою. Захист поширюється на адміністраторів; force push і видалення заборонені. Обов'язкове схвалення другого людського рев'юера не потрібне. Не вимикай захист для обходу падіння перевірок.

## 4. Готовність і перевірки

Перевіряй змінену поведінку відповідними тестами. Для важливих користувацьких сценаріїв перевіряй основний шлях і релевантний збій. Для виправлення помилки, коли це практично, спочатку відтвори її та додай тест, який падає до виправлення.

Не послаблюй перевірки й не додавай повторні прогони, щоб приховати невідому причину падіння. Спочатку з'ясуй причину. Не називай успішну збірку доказом працездатності всієї фічі. Розрізняй локальні перевірки, hosted CI, preview і production.

CI запускається на push у всі гілки та PR до `develop` і `main`. Зберігай обидва jobs: `checks` (unit-тести, build, TypeScript) та `integration` (ізольований Supabase, API/база/Storage і браузерні сценарії). Команди та межі покриття описані в [docs/ci.md](docs/ci.md).

## 5. Дані та експлуатація

Використовуй ізольовані тестові середовища. Не підключай тести до production і не скидай робочу базу. Для інтеграційних перевірок використовуй окремий `read-together-ci` з [docs/ci.md](docs/ci.md); прибирай лише його тестові ресурси. Preview сам по собі не гарантує ізоляції даних: перед тестуванням перевір, що його backend також тестовий.

Перед релізом із міграціями визначай порядок застосування, сумісність старого та нового коду й спосіб відновлення даних та коду. Міграції production і deployment потребують явного доручення згідно з розділом 2.

## 6. Звіт про результат

Після задачі коротко повідомляй:

- що змінилося і чому;
- що перевірено та що лишилося неперевіреним;
- гілку й коміти;
- чи виконані push, merge, міграція та deployment.

Не називай локальні або лише опубліковані в робочій гілці зміни production-релізом.
